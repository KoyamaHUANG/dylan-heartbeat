# Dylan Heartbeat V1.2 — Proactive Message Safety Fix

## Incident

The Railway forensic audit identified proactive message `dcac217c-8f33-4c4f-8520-e50786a773e2` / event `4259d42a-264f-4a87-9b41-9f1a74133193` as an unsafe multi-turn continuation. Its six anomalous anchors did not appear in history before the generated proactive message. This change does not alter `archive_messages.id=83`, any historical chat, or any Railway Volume data.

The expected forensic-audit report filename was not present in this checked-out worktree. The incident facts above and the supplied audit findings were treated as the source of truth for this local-only repair.

## Root Cause

`wake_up.js` formatted history as open-ended `[用户]` / `[AI]` transcript text inside a normal user message. It accepted unrestricted model text, stripped a few presentation markers, and only then used a 500-character limit. Therefore a model could continue the transcript and have the resulting text reach Bark, the proactive event store, archive capture, and Kelivo sync. `enhanced_messages.json` and `kelivo_sync_context.json` were also global state, so the last active binding could be reused by another conversation.

## Fix

- Wake generation now requests an API-level `json_schema` contract by default: `{"action":"send"|"skip","title":"...","body":"..."}`. `json_object` and no-structured-output modes remain explicit compatibility options, but all responses still undergo strict JSON parsing and server-side schema checks.
- A parse or schema failure fails closed. Raw provider text is never promoted to a notification body.
- History is passed as read-only JSON `recent_history` objects, not a role-labelled transcript.
- `proactive_safety.js` rejects high-confidence role markers, multi-role transcript lines, and `<current_time>` tags. Validation occurs on the complete parsed body before the display-only 500-character limit.
- The Gateway validates again before creating a proactive event or scheduling archive capture. Invalid payloads are rejected before timeline/event/archive work.
- The event store validates new writes while preserving pre-existing stored events exactly, including historic evidence that would not meet the new rule.
- `proactive_generation_audit.json` records hashes and safe metadata only: request/event identity, binding, model, timestamp, context/output/body hashes, validation, push status, and archive lifecycle. It first records `scheduled`, then the asynchronous capture callback updates the same `request_id + event_id` record to `success` with the UUID `archive_message_id`, or `failed` with a safe error code and completion timestamp.

## Safety Boundary

Rejected output records only a structured reason such as `role_transcript_detected`, `current_time_tag_detected`, or `structured_output_parse_failed`; it does not log the raw model body. Rejection causes no Bark/ntfy call, no internal wake event, no proactive event, and no archive capture. The truncation limit runs only after complete-body validation.

## Conversation Isolation

- Bound chats now use `conversation_state/<sha256(assistant_id,conversation_id)>/` for their timeline and timestamp memory.
- A V2 context registry stores multiple exact bindings in `kelivo_sync_context_v2.json`.
- Wake enumerates only V2 bindings and validates the target identity again at the Gateway boundary.
- The old global `enhanced_messages.json` and `kelivo_sync_context.json` are preserved for ordinary legacy chat compatibility but are not migrated, guessed, or used as wake targets. A partial conversation-only header remains legacy-unbound and cannot activate a wake target.

## Tests

New `test/proactive_safety.test.js` covers all ten requested scenarios: valid send; incident transcript; current-time tags; malformed JSON; skip; normal over-500 body; violation after 500 characters; cross-conversation isolation; cross-assistant isolation; and legacy global-state rejection. It also covers provenance archive success, failure with redacted error metadata, reverse-order concurrent completion, and P0 regression. `test/proactive_events.test.js` additionally proves old stored events are retained while new unsafe writes fail.

Full local suite: `node --test` — 103 total, 100 passed, 0 failed, 3 skipped. The skipped tests are the existing opt-in real PostgreSQL / real-format dependency cases. `npm test` was unavailable because `npm` was not on PATH; the package script is exactly `node --test`, which was run directly.

## Compatibility

Normal chat forwarding, Bark/ntfy successful sends, proactive-event pulls and sequence allocation, Raw Chat Archive capture, and the existing archive identity contract remain in place. Legacy clients still receive ordinary chat service; without a complete assistant-plus-conversation identity they simply cannot be selected for proactive wakeups.

## Remaining Risks

- A provider that does not support the default JSON Schema mode must be configured for its supported structured mode; it will still fail closed if it returns non-JSON.
- Archive capture remains intentionally asynchronous/fail-open. `scheduled` is transient: its callback updates the same provenance record to `success` or `failed`; it can remain scheduled only if the process terminates before callback completion.
- High-confidence text rules intentionally do not attempt to detect every possible natural-language imitation of a dialogue, so ordinary Chinese notification text is not broadly rejected.

## Deployment Plan

1. Human review this diff and the report.
2. Confirm the target provider supports the selected structured-output mode in a non-production environment with mocked or controlled calls.
3. Deploy through the normal approved release process only after review.
4. Monitor hash-only provenance and validation-rejection metadata; do not log raw prompts or outputs.

At the time of this report's local validation, this change had not deployed, restarted Railway, written to Railway, sent a real proactive message, or modified historical chat.
